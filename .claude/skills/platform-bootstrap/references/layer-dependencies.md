# Layer Dependencies — Why the Scaffold Order Matters

Each phase of bootstrap depends on the previous one being *addressable* — not just defined, but actually reachable over the network with credentials that work. Reordering causes silent failures masked as configuration bugs.

## The dependency graph

```
infra runtime          ← everything depends on the network + named volumes existing
    └─ storage init    ← schemas / buckets must exist before any service connects
        ├─ orchestrator   ← stores its metadata in the storage layer
        │   └─ glue       ← orchestrator pulls dbt manifests, registers ingestion assets
        │       └─ quality
        ├─ transformation ← reads warehouse, writes marts
        └─ ingestion      ← writes raw to storage
```

## What breaks when reordered

### Scaffolding transformation before storage init

dbt's first command (`dbt debug`) opens a connection to the warehouse. If the warehouse schema doesn't exist, dbt either:
- Fails with a credentials error (misleading — credentials are fine)
- Succeeds against `PUBLIC` and silently writes models there, leading to a mess to migrate later.

Always create the dbt schema before `dbt debug`.

### Scaffolding orchestrator before its metadata store

Dagster's webserver and daemon need a Postgres backend (or SQLite for local). If the backend isn't ready, the daemon enters a restart loop that looks like a Dagster bug. Healthchecks (see `infra-docker-compose` references) prevent this — but only if the metadata DB is in the storage init phase, before the orchestrator scaffolds.

### Scaffolding ingestion before any consumer exists

It's tempting to load all 5 sources before scaffolding dbt. Don't:
- You waste the most exploratory time on the layer with the least feedback (raw data tells you little until transformations consume it).
- Schema decisions made in ingestion lock down before transformation gets to weigh in.
- The verify step at the end has nothing to consume the loads.

Load **one** source. Build the first staging model on top of it. Then scale.

### Adding glue before transformation has a model

Dagster's `dbt_assets` factory needs a dbt manifest. The manifest is generated by `dbt parse` or `dbt compile`, which requires at least one valid model. Without that, the glue silently registers an empty asset graph and the user thinks Dagster doesn't see dbt.

### Adding quality before there's anything to test

A `dbt test` against an empty project passes vacuously. An asset check against a never-materialized asset is meaningless. Quality verifies real artifacts; bootstrap is done with example tests that prove the wiring, not the data.

## When reordering is okay

- **Skipping ingestion entirely** — if data is already in the warehouse (the project is transformation-only), skip steps 5 and 6, keep the rest in order.
- **Skipping orchestrator for a quick POC** — pure `dbt` projects without an orchestrator are valid; verify with `dbt run` directly. Add orchestrator later when scheduling matters.
- **Parallel work after step 4** — once orchestrator + transformation are both up, ingestion and quality work can proceed in either order or in parallel.

## Checkpoint per step

Each scaffold step ends with a check. Move on only when the check passes:

| Step | Check |
|---|---|
| 1. Infra runtime | `docker compose ps` shows every base service `(healthy)` |
| 2. Storage init | Connect from a sibling container; the expected DB / bucket / schema exists |
| 3. Orchestrator | Webserver UI loads; workspace is empty but valid |
| 4. Transformation | `dbt debug` passes; a no-op `dbt run` succeeds |
| 5. Ingestion | One pipeline writes one table end-to-end |
| 6. Glue | Orchestrator asset graph shows ingestion → transformation lineage |
| 7. Quality | At least one example test runs and passes |
